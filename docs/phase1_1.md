# CrossLLM Phase 1 补充：实际对话模式与上下文策略 v1.1

## 1. 补充原因

Phase 1 原始任务主要验证：

* Session
* Model Lifecycle
* Round
* Persistence
* Cross-Round Context
* Anonymous Peer Context

在 Phase 1 / Phase 2 实际使用过程中，发现原任务书对“用户每次发送消息时到底选择哪些模型、是否进行互评、读取多少历史”定义不足。

本补充不推翻原 Phase 1。

它只补充实际使用所需的交互规则，并保持现有核心架构。

---

## 2. 模型选择

CrossLLM 的模型参与由用户通过模型选择控件决定。

### 2.1 ACTIVE 模型

ACTIVE 模型可以被用户选择。

### 2.2 CLOSED 模型

CLOSED 模型不得被选择。

UI 中：

* CLOSED 模型仍然显示；
* 保留历史回答；
* 对应 checkbox 必须 disabled；
* 用户不能通过本轮操作重新让 CLOSED 模型参与。

### 2.3 单模型与群发

本系统不额外设置“单聊 / 群发”模式按钮。

根据本次选中的 ACTIVE 模型数量自动决定：

```text
选择 0 个模型
→ 不允许发送

选择 1 个模型
→ 单模型对话

选择 2 个及以上模型
→ 群发
```

因此：

> **群发只是“同一次用户输入发送给多个模型”的结果，而不是独立的业务模式。**

---

## 3. 互评开关

多模型群发与互评不是同一个功能。

互评是一个独立的可选开关。

### 3.1 互评关闭

```text
用户问题
   ↓
所选模型分别获得自己的对话上下文
   ↓
独立生成回答
```

不向模型注入其他模型的回答。

### 3.2 互评开启

```text
用户问题
   ↓
所选模型分别生成回答
   ↓
下一轮允许读取其他参与模型的历史回答
   ↓
以匿名 Candidate 身份交叉注入
```

互评开启并不意味着必须长期保留互评历史。

每次是否传递其他模型回答，由当前互评开关决定。

### 3.3 单模型情况下

如果本次只有一个模型参与：

```text
互评开启
→ 没有其他模型可供互评
→ 等价于关闭互评
```

不产生无意义的 Candidate。

---

## 4. Cross-Round Context 策略

CrossLLM 不默认无限累积历史。

第一版使用固定的“最近三轮”窗口。

### 4.1 默认历史窗口

对于当前 Round N：

```text
优先读取：

Round N-1
Round N-2
Round N-3
```

更早的 Round 默认不进入当前模型上下文。

即：

```text
N
├── N-1   ✅
├── N-2   ✅
├── N-3   ✅
├── N-4   ❌
└── N-5   ❌
```

### 4.2 为什么默认保留最近三轮

本项目主要用于个人技术问答、头脑风暴和问题讨论。

最近几轮通常包含：

* 上一轮模型的最新判断；
* 对上一轮观点的修正；
* 用户追加的问题；
* 最近形成的结论。

继续向更早历史扩展会增加：

* 重复内容；
* 已被后续观点否定的旧观点；
* 无关上下文；
* 模型注意力分散的可能性。

因此 Phase 1/Phase 2 第一版不做无限历史。

---

## 5. Context 超限时的处理

“最近三轮”是上限，不代表每次都必须完整塞入三轮。

发送前应进行基础长度检查。

### 5.1 优先级

上下文优先级：

```text
当前用户指令
      ↓
Round N-1
      ↓
Round N-2
      ↓
Round N-3
```

### 5.2 超限处理

如果加入三轮后超过模型允许的上下文预算：

```text
先移除最旧的 Round N-3
↓
仍超限
↓
移除 Round N-2
↓
仍超限
↓
只保留 Round N-1
```

不进行：

* LLM 自动摘要；
* 历史相关性检索；
* 复杂上下文压缩；
* 多阶段摘要。

### 5.3 单轮仍过长

如果 Round N-1 单独已经接近或超过可用上下文：

第一版只进行最小保护，不设计复杂压缩算法。

实现可以根据实际 Provider 能力选择：

* 截断；
* 拒绝发送并提示；
* 使用 Provider 提供的 context limit 检查。

具体行为应保持简单、可解释。

---

## 6. Token 统计与 Context 预算

### 6.1 Phase 1

Phase 1 使用 Mock Provider，不要求精确 token 统计。

只要求：

* 不无限注入历史；
* 默认最多读取最近三轮；
* 发送前具备基本的长度保护。

### 6.2 Phase 2

真实 Provider 可以获取实际 token usage 时，应优先使用 Provider 返回的真实数据。

例如：

```json
{
  "input_tokens": 18240,
  "output_tokens": 2138
}
```

实际 token 数优先于字符估算。

### 6.3 Token 估算

在请求发送前，如果无法得到 tokenizer 的精确计算结果：

可以使用简单估算仅用于：

> **避免明显超过 context 上限。**

该估算不作为计费依据，不作为模型质量指标。

不引入复杂 tokenizer 系统作为本阶段必要依赖。

---

## 7. 与匿名互评的关系

本补充不改变原 Phase 1 的匿名约束。

当互评开启并存在多个参与模型时：

```text
自己的历史回答
+
其他 ACTIVE 模型历史回答
```

仍然通过匿名 Candidate 身份传递。

不得因为增加“最近三轮”而改变：

* model_id 与 candidate_id 的分离；
* CLOSED 模型排除；
* Round 1 独立性；
* Candidate 标签规则。

---

## 8. 与原 Phase 1 的兼容性

本补充不修改原有核心验收：

* ACTIVE / CLOSED；
* Round 独立；
* Persistence；
* Session Recovery；
* Anonymous Peer Context；
* CLOSED 历史保留；
* Round 1 不读取其他模型；
* Round 2 可以读取上一轮。

本补充只是增加用户层面的对话选择行为和历史窗口规则。

---

## 9. 第一版明确不做

以下功能不属于当前实现要求：

* 自动判断用户是否需要群发；
* 自动判断用户是否需要互评；
* 无限历史；
* 历史相关性检索；
* LLM 自动总结旧历史；
* 注意力分析；
* reasoning 过程评估；
* Tool / MCP 搜索过程评估；
* 搜索结果质量评分；
* 模型内部思考质量评分。

CrossLLM 仍然只关注：

> **模型最终回复及其跨 Round 的交叉反馈。**

---

## 10. 当前最终交互逻辑

用户每次发送消息时：

```text
              用户输入
                  ↓
          选择 ACTIVE 模型
                  ↓
        ┌─────────┴─────────┐
        ↓                   ↓
      1 个                多个
        ↓                   ↓
     单模型                群发
        │                   │
        └─────────┬─────────┘
                  ↓
             互评开关？
             /       \
           OFF       ON
            ↓         ↓
        独立回答   匿名交叉回答
                     ↓
             最多读取最近三轮
                     ↓
               Context 预算保护
                     ↓
                 最终回复
```

---

## 11. 设计原则

CrossLLM 是个人研究与头脑风暴工具。

优先：

* 简单；
* 低依赖；
* 可运行；
* 可验证；
* 实际好用。

只有在实际使用中发现问题时，才增加复杂度。

不要为了理论上的“完整上下文管理”或“生产级架构”提前引入额外系统。
